## 1. Project Architecture and Folder Structure

### 1.1 Existing Project Overview

The **ONYX Backend** (`onyx-be`) is a production REST API built with **Node.js**, **Express**, **TypeScript**, and **PostgreSQL** via **TypeORM**. It incorporates Role-Based Access Control (RBAC), Joi schema validation with `express-validation`, internationalization (i18n) in 5 languages, background queuing via **BullMQ** on **Redis**, Cloudflare R2 / S3 object storage for chunked multipart uploads, and PDF generation with `wkhtmltopdf`.

### 1.3 Architectural Layer Flow & Responsibilities

The system follows a strict, unidirectional architectural flow:

```
HTTP Client Request
         │
         ▼
[1. Express Loader & Middlewares]   (CORS, JSON 50MB, fileUpload, languageMiddleware)
         │
         ▼
[2. Route Definition]               (Mounts URL, applies authenticate/authorize)
         │
         ▼
[3. RBAC Permission Middleware]     (checkPermissions checks role vs allRoles map)
         │
         ▼
[4. Joi Validation Middleware]      (Validates params, query, body with context)
         │
         ▼
[5. Controller]                     (Parses input, invokes service, emits sendResponse)
         │
         ▼
[6. Service Layer]                  (Executes business logic, orchestrates queries/queues)
         │
         ▼
[7. Data Access / Query / Model]    (TypeORM Repositories, QueryRunner, Entities)
         │
         ▼
[8. Database / Storage / Queue]     (PostgreSQL, Redis / BullMQ, Cloudflare R2)
```

#### Layer Responsibilities

| Layer | Responsibility | What It MUST Do | What It MUST NEVER Do |
| :--- | :--- | :--- | :--- |
| **Routes** (`src/routes/`) | Endpoint binding & middleware chaining | Define path, attach `checkPermissions`, attach `validate()`, delegate to controller | Never write inline business logic or access DB |
| **Middlewares** (`src/middlewares/`) | Request interception & context enrichment | Verify JWT (`authorize`), check permissions (`permission`), set `req.user` & `req.language` | Never emit business responses; only call `next()` or `next(err)` |
| **Validators** (`src/validators/`) | Schema definition & input boundary protection | Validate `body`, `query`, `params`, `headers` via Joi; use `Joi.ref('$user.role')` for context | Never execute database queries inside validators |
| **Controllers** (`src/controllers/`) | HTTP parameter extraction & response transport | Extract typed params from `req`, call service methods, invoke `sendResponse(res, ...)` | **Never execute direct raw SQL queries or complex business logic** |
| **Services** (`src/services/`) | Core business rules & orchestration | Coordinate DB transactions, external APIs (AI, R2, Mail), background job dispatching | Never access Express `req` or `res` objects directly |
| **Queries / Models** (`src/queries/`, `src/models/`) | Database projection, schema & mapping | Encapsulate `FindOptionsSelect`, TypeORM entity mappings, query builder filters | Never contain transport-layer or HTTP response logic |
| **Queues & Workers** (`src/queues/`, `src/workers/`) | Asynchronous, decoupled background tasks | Process emails, thumbnail generation, orphan file cleanup via BullMQ | Never block HTTP request threads for slow operations |

### 1.4 Placement Rules for New Files

| If you are adding... | Place it in... | Follow this naming pattern... |
| :--- | :--- | :--- |

## 2. File and Folder Naming Conventions

### 2.1 File & Folder Naming Rules

- **Folders**: Lowercase `kebab-case` plural or singular per architectural category (e.g. `controllers`, `services`, `middlewares`, `database/migrations`).
- **Files**: All TypeScript source files MUST use `kebab-case.<category>.ts`.

```text
[feature-name].[category].ts
```

| Category | Suffix | Example |
| :--- | :--- | :--- |
| **Controller** | `.controller.ts` | `src/controllers/audit-log.controller.ts` |
| **Service** | `.service.ts` | `src/services/admin-dashboard.service.ts` |
| **Route** | `.route.ts` | `src/routes/project-option.route.ts` |
| **Validator** | `.validator.ts` | `src/validators/contact-submission.validator.ts` |
| **Model (Entity)** | `.model.ts` | `src/models/lca-benchmark.model.ts` |
| **Type Definition** | `.type.ts` *(never plural)* | `src/types/company.type.ts` |
| **Enum** | `.enum.ts` | `src/enums/external-report.enum.ts` |
| **Constant** | `.constant.ts` | `src/constants/permission.constant.ts` |
| **Utility** | `.util.ts` | `src/utils/pagination.util.ts` |
| **Middleware** | `.middleware.ts` | `src/middlewares/permission.middleware.ts` |
| **Queue** | `.queue.ts` | `src/queues/media-cleanup.queue.ts` |
| **Worker** | `.worker.ts` | `src/workers/media-processing.worker.ts` |
| **Seeder** | `.seeder.ts` | `src/database/seeds/project-options.seeder.ts` |

## 4. TypeScript Types, Interfaces, and Enums

### 4.1 When to Use `interface` vs `type`

| Construct | When to Use | Example |
| :--- | :--- | :--- |
| **`interface`** | Object shapes, request payloads, response bodies, model projections, query parameters. Must start with `I`. | `export interface IUserResponse { ... }` |
| **`type`** | Unions, intersections, primitives, utility types, `keyof` expressions. | `export type NonAdminUserRole = Exclude<UserRole, UserRole.ADMIN>;` |
| **`enum`** | Fixed sets of domain options stored in DB or validated in API. | `export enum UserStatus { ACTIVE = 'active', ... }` |

### 4.2 Type Suffix Standard

Standardize type naming suffixes according to their purpose:

| Suffix | Purpose | Example |
| :--- | :--- | :--- |
| **`...Payload`** | HTTP Request Body payloads | `IProjectPayload`, `IUserUpdatePayload`, `ICreateAuditLogPayload` |
| **`...Query`** | HTTP URL Query string parameters | `IUserListQuery`, `IProjectListQuery`, `IAuditLogListQuery` |
| **`...Params`** | URL path parameters or internal function options | `IEpdCompanyFilterParams`, `IBuildStoragePathParams` |
| **`...Response`** | Standard HTTP API `data` payload | `IUserResponse`, `IMediaResponse`, `IAdminDashboardResponse` |
| **`...Item`** | Individual element within a list or array response | `IRecentProjectItem`, `IAuditLogListItem`, `INotificationItem` |
| **`...Row` / `...Raw`** | Direct raw database query output | `IUserRawQueryRow`, `ILcaBenchmarkRaw` |

> [!WARNING]
> **Do not use `Dto` or `Input` suffixes.** The established convention in this project is `Payload` for request bodies, `Query` for query parameters, and `Response` for response bodies.

### 4.3 Strictness & Eliminating `any`

The compiler is configured with `"strict": true` and `"noUnusedLocals": true`.
- **Never use `any`**: Use `unknown` with type narrowing (e.g. `typeof`, `instanceof`, or custom type guards) or use generic type parameters.
- **Never use unsafe type assertions** (`as any` or `as unknown as Type`) unless interfacing with third-party libraries that lack complete typing.

```typescript
// ❌ FORBIDDEN: Forcing types with any
this.gross_floor_area = formatCleanNumber(this.gross_floor_area) as any;

// ✅ CORRECT: Proper return typing or null-coalescing
const cleanedNumber: number | null = formatCleanNumber(this.gross_floor_area);
this.gross_floor_area = cleanedNumber !== null ? String(cleanedNumber) : null;
```

### 5.3 HTTP Status Code Conventions

- `200 OK`: Successful read, update, or action execution.
- `201 Created`: Successfully created resource (or 200 with success envelope).
- `400 Bad Request`: Malformed request, invalid syntax, or failed Joi validation.
- `401 Unauthorized`: Missing token, invalid token format, expired session, or deactivated account.
- `403 Forbidden`: Authenticated user lacks the required RBAC permission for this endpoint.
- `404 Not Found`: Target entity does not exist.
- `409 Conflict`: Unique constraint violation (e.g. duplicate email or project name).
- `422 Unprocessable Entity`: Business rule failure (e.g. password mismatch or invalid state transition).
- `500 Internal Server Error`: Unhandled exception or infrastructure failure.

## 8. Error Handling and Logging

### 8.1 Exception Hierarchy (`src/utils/error.util.ts`)

Throw custom exceptions from services and utility functions. Do not return raw error objects or manually construct error responses in controllers.

```typescript
import {
  BadRequestException, // 400 - Validation or bad input
  AuthException,       // 401 - Authentication failure
  ForbiddenException,  // 403 - Permission denied
  NotFoundException,   // 404 - Record not found
  ExistException,      // 409 - Record already exists
  NotMatchException,   // 422 - Business logic mismatch (e.g. wrong password)
  ServerException,     // 500 - Server failure
} from '@util/error.util';

if (!user) {
  throw new NotFoundException('user.user_not_found');
}
```

### 8.2 Controller Error Propagation

Controllers MUST wrap operations in `try / catch` and forward unhandled exceptions to `next(error)`:

```typescript
async function getUser(req: Request, res: Response, next: NextFunction) {
  try {
    const user = await userService.getUserById(req.params.id);
    return sendResponse(res, user, 'user.user_details_retrieved');
  } catch (error) {
    return next(error);
  }
}
```

### 8.3 Logging Standards

```typescript
import Logger from '@logger/index';

// ✅ CORRECT: Structured logging
Logger.info('User logged in successfully: %s', user.id);
```

## 9. Validation and Data Handling

### 9.1 Joi Schema Definition (`src/validators/`)

All HTTP endpoints must validate their inputs using Joi schemas applied via `express-validation`:

```typescript
// src/validators/user.validator.ts
import Joi from 'joi';
import { UserRole, UserStatus } from '@enum/user.enum';

const userParams = {
  listUsers: {
    query: Joi.object({
      page: Joi.number().integer().min(1).default(1),
      per_page: Joi.number().integer().min(1).max(100).default(10),
      search: Joi.string().trim().optional().allow('', null),
      role: Joi.string().valid(...Object.values(UserRole)).optional(),
      status: Joi.string().valid(...Object.values(UserStatus)).optional(),
      fetch_all: Joi.boolean().optional(),
    }),
  },
  getUser: {
    params: Joi.object({
      id: Joi.string().trim().uuid().required(),
    }),
  },
};

export default userParams;
```

### 9.2 Context-Aware RBAC Validation

Because `loaders/express.ts` configures `validateOptions = { context: true }`, you can reference the authenticated user within Joi schemas using `Joi.ref('$user.role')`:

```typescript
company_id: Joi.when(Joi.ref('$user.role'), {
  is: UserRole.ADMIN,
  then: Joi.string().trim().uuid().optional().allow(null),
  otherwise: Joi.forbidden(),
});
```

## 10. Database and Backend Standards

### 10.1 TypeORM Entities & PostgreSQL Naming

- Tables: `snake_case` plural (`users`, `companies`, `projects`).
- Columns: `snake_case` (`company_name`, `created_at`, `deleted_at`).
- Models: `src/models/<domain>.model.ts` configured with `SnakeNamingStrategy()`.
- Primary Keys: Always UUID v4 generated via `@PrimaryGeneratedColumn('uuid')`.
- Soft Deletion: Always include `@DeleteDateColumn() deleted_at: DateTime | null;` and ensure queries check `deleted_at IS NULL` or use TypeORM's built-in soft delete features.

### 10.2 Database Migrations (Mandatory)

**Never manually modify database schemas.** Every schema change must be executed through a TypeORM migration:

```bash
# Generate migration from entity changes
npm run migration:generate

# Create blank migration for custom SQL
npm run migration:create

# Execute pending migrations
npm run migration:run

# Revert the latest migration
npm run migration:revert
```

### 10.3 Safe Queries & SQL Injection Prevention

When executing raw SQL queries via `AppDataSource.query(...)`, **ALWAYS use parameterized queries (`$1`, `$2`)**:

```typescript
// ✅ CORRECT: Parameterized query
const users = await AppDataSource.query(
  `SELECT * FROM users WHERE role = $1 AND deleted_at IS NULL`,
  [UserRole.MANUFACTURER],
);

// ❌ FORBIDDEN: Vulnerable string concatenation
const users = await AppDataSource.query(
  `SELECT * FROM users WHERE role = '${req.query.role}'`,
);
```

### 10.4 Transaction Handling

When performing multi-table mutations (e.g. creating a User and an associated Company simultaneously), execute within a transaction:

```typescript
const queryRunner = AppDataSource.createQueryRunner();
await queryRunner.connect();
await queryRunner.startTransaction();

try {
  const company = await queryRunner.manager.save(Company, companyData);
  user.company_id = company.id;
  await queryRunner.manager.save(User, user);

  await queryRunner.commitTransaction();
} catch (error) {
  await queryRunner.rollbackTransaction();
  throw error;
} finally {
  await queryRunner.release();
}
```
